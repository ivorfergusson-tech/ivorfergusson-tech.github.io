Project 01

Embodied Carbon Calculator

An Excel model that estimates how much carbon a building's materials release before the building is even used, and shows how material choices change that figure.

PythonopenpyxlExcel (live formulas)ICE Database v4.1BS EN 15978
Download the workbook (.xlsx)
S

Situation

UK construction companies must comply with carbon reporting, reduction and net-zero requirements, including SECR reporting, Scope 1–3 emissions accounting and building regulations that target low-carbon construction. Firms increasingly need to estimate how much carbon a project will release at design stage.

T

Task

Build a transparent, reusable tool that estimates a project's embodied carbon, where every result can be traced back to a quantity, a density, a waste allowance and a cited carbon factor, rather than being an unexplained number.

A

Action

Wrote a Python script (openpyxl) that generates an Excel workbook with five tabs: Read Me, Methodology, Carbon Factors, Calculator and Summary. Every result cell is a live Excel formula (VLOOKUPs into the factor table), not a pasted value, so anyone can click a cell and see how it was calculated.

Material factors come from the industry-standard ICE Database. Dropdowns prevent typos, and 15 blank formula rows let the workbook be reused for a new project without touching code.

R

Result

A worked example (a small single-storey domestic extension) gives about 4.1 tonnes CO₂e across modules A1–A5. The concrete foundation and facing brick are the biggest contributors. A built-in comparison shows that switching the rebar from UK recycled to virgin steel increases its material carbon by about 4.4×.

How it works

The model follows the life-cycle stages defined in BS EN 15978. Each row of the calculator is one building element (e.g. the strip footing), and it passes through these steps:

  1. Step 1Quantity
  2. Step 2Mass + waste
  3. Step 3 · A1–A3Material carbon
  4. Step 4 · A4Transport
  5. Step 5 · A5Construction
  6. Step 6Total & chart
1. Quantity
Enter the element, pick a material from the dropdown, and type in the quantity from the take-off, in m³ or kg.
2. Mass + waste
Volumes are converted to mass using the material's density (IF(unit="m3", qty×density, qty)), then increased by a typical waste allowance (e.g. 5% for concrete, 10% for brick) to reflect over-ordering and offcuts.
3. Material carbon (A1–A3)
Mass × the ICE carbon factor (kgCO₂e per kg) covers "cradle to gate": extracting raw materials, transporting them to the factory and manufacturing the product.
4. Transport (A4)
tonnes × km × 0.105: the carbon from lorries delivering materials to site, using an editable distance and an average UK HGV emission factor.
5. Construction (A5)
A default percentage (5%) of A1–A4 to cover site energy and plant. RICS whole-life carbon guidance allows this when detailed site data isn't available yet.
6. Total & chart
Each row's A1–A5 figures are summed and converted to tonnes. The Summary tab charts carbon by element, so the biggest "hotspots" are obvious at a glance.
Honest limitationsCarbon factors, waste allowances and the transport factor are representative values rather than live data. A real project would use supplier EPDs and actual delivery distances. The scope is A1–A5 only, so in-use and end-of-life stages are excluded, and the timber figure excludes biogenic carbon storage. The tool is still being refined.
Project 02

Quantity Take-off & Cost Estimator

A browser tool that mirrors a construction estimator's workflow, from measured drawing dimensions to a priced Bill of Quantities and a tender-ready Excel pack.

JavaScriptHTML / CSSSheetJS (Excel export)localStorageGitHub Pages
Open live demo View source code
S

Situation

During my internship at Lambert Construction I supported the estimating team with quantity take-offs and cost-estimate reviews for upcoming tenders. I saw that pricing a job is a careful, step-by-step process, not a single guess.

T

Task

Build a tool that reproduces the four real estimating stages (measure → abstract → price → summarise) so I could properly understand and explain each one, and produce an output an estimator could actually check.

A

Action

Split the logic into small JavaScript modules, each with one job: takeoff.js squares dimensions, boq.js groups and prices items, estimate.js adds on-costs, and xlsx-export.js writes the Excel file.

Built a rate library with separate labour, material and plant rates, and a sample project ("Riverside Apartments, Block C") with 15 measured lines across groundworks, concrete, masonry, drainage and externals.

R

Result

A working, publicly hosted tool that takes measured dimensions and produces a priced BOQ and tender summary, then exports an Excel tender pack with live formulas on separate Takeoff, BOQ and Summary sheets, so every number can be checked the way you would check a colleague's estimate.

How it works

The tool has one screen for each stage an estimator goes through:

  1. Step 1Take-off
  2. Step 2Abstract to BOQ
  3. Step 3Rate build-up
  4. Step 4Tender summary
  5. Step 5Excel export
1. Take-off
Enter what was measured from the drawing: location, description, dimensions and "timesing" (how many times it repeats). Squaring multiplies them into a quantity: times × L × W × D.
2. Abstract to BOQ
The same item is measured in many places (e.g. blockwork wall by wall). Abstracting groups every measurement of that item into one Bill of Quantities line, so you price "450 m² of blockwork" once.
3. Rate build-up
Each BOQ line gets a £/unit rate built from labour + material + plant. Quantity × rate = line cost. Showing the build-up means a price can be justified rather than guessed.
4. Tender summary
On top of the measured work the tool adds preliminaries (running the site), overheads & profit and contingency (a risk buffer). Change a percentage and the tender sum updates instantly.
5. Excel export
SheetJS writes a real .xlsx with formulas in the cells, not just numbers, so the file behaves like an estimator's own spreadsheet and can be audited line by line.
Behind the scenes
With no server needed, project data is saved in the browser. The costing maths is kept separate from the screen code, so any number can be traced to the one file that calculated it.
Honest limitationsIt does not read CAD or PDF drawings automatically, and assumes the drawing has already been measured (commercial software like CostX or Bluebeam does that part). Unit rates are illustrative, not live BCIS or supplier prices, so the bill may not be commercially accurate. Prelims, OH&P and contingency are applied as flat percentages.
Project 03

Site Diary & Defect Log

A web app that turns simple form entries into the two documents every site runs on: a professional daily site report and a defect register, both downloadable as PDF.

JavaScriptHTML / CSSjsPDFlocalStorageGitHub Pages
Open live demo View source code
S

Situation

On site, the daily diary is the contractor's evidence of what happened each day (labour, plant, weather, deliveries, instructions and delays). It is used in delay claims and extension-of-time disputes. Missing or vague diaries cause real problems, and defects must be tracked all the way to close-out.

T

Task

Build a simple tool that captures both records with realistic fields, and automatically produces a properly formatted document from them, the same idea as site software like Procore or Fieldwire, but on a small scale.

A

Action

Built two forms: a Site Diary (labour, plant, weather, deliveries, instructions, delays, H&S notes) and a Defect Log (location, severity, raised by, assigned to, and status from raised → assigned → closed).

Wrote a report module that renders the saved entries as a formatted daily report or defect register on screen, and a second renderer that draws the same content onto a PDF with jsPDF.

R

Result

A live, free-to-use app where typed-in entries become a professional daily report or defect register in one click, viewable on screen or downloadable as a PDF. It also gave me a real understanding of why site records matter commercially, not just administratively.

How it works

Everything runs in the browser. Data flows through four stages:

  1. Step 1Form → data
  2. Step 2Data → storage
  3. Step 3Storage → report
  4. Step 4Report → PDF
1. Form → data
When you submit a diary or defect form, the browser's built-in FormData reads every field into a single data object.
2. Data → storage
That object gets an ID and timestamp and is saved as JSON in the browser's localStorage, so entries survive a page refresh.
3. Storage → report
The app re-reads everything saved and lays it out as a formatted daily report (for diaries) or a table register (for defects).
4. Report → PDF
jsPDF draws the same information onto a PDF page, placing text at x/y coordinates. That is how PDF generation genuinely works, because a PDF has no HTML inside it.
Honest limitationsThere is no backend, so data is saved only in the browser on that device and is not shared between users. A real version would need a database and logins. Photos are stored as embedded text, which wouldn't scale to a live site. Because all storage goes through one file, swapping in a real database would only mean changing that one file.
